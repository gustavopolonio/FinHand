# FinHand — Data Model

## Purpose and scope

This document defines FinHand's initial PostgreSQL data model and the boundaries for future milestone-specific extensions.

The first database migration will contain the financial core:

- `users`
- `accounts`
- `categories`
- `transactions`

Milestone 2 adds Google authentication through Better Auth using the existing
`users` table plus `auth_accounts`, `auth_sessions`, and `auth_verifications`.

Tables for uploads, AI extraction, audio transcription, and RAG are described as planned extensions but will be introduced only in their corresponding milestones.

## Design principles

- Every financial record is owned by one user.
- Ownership is enforced through foreign keys as well as application authorization.
- Monetary values use integer minor units and must never be converted to floating-point values.
- AI-extracted data is a candidate until the user explicitly confirms it.
- Current account balances are calculated from immutable financial facts rather than stored as mutable values.
- Records referenced by financial history are archived instead of physically deleted.
- PostgreSQL native enums are avoided initially; text columns with check constraints are easier to evolve through migrations.
- All identifiers are UUIDs generated by PostgreSQL.
- Audit timestamps use `TIMESTAMPTZ` and are stored in UTC.

## Entity relationship overview

```text
users
 ├── 1:N accounts
 ├── 1:N categories
 ├── 1:N transactions
 │        ├── N:1 account
 │        └── N:0..1 category
 ├── 1:N auth_accounts
 └── 1:N auth_sessions
```

All accounts, categories, and transactions are private to their owning user.

## Core entities

### `users`

Represents a FinHand user and is the ownership boundary for financial data. Better Auth reuses this table for the Google-authenticated identity so financial records can reference the authenticated user directly.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `uuid` | No | Primary key; defaults to `gen_random_uuid()` |
| `email` | `text` | No | Normalized email address |
| `display_name` | `text` | Yes | User-facing name |
| `email_verified` | `boolean` | No | Whether the identity provider verified the email address |
| `image_url` | `text` | Yes | Optional Google profile image URL |
| `default_currency` | `varchar(3)` | No | ISO 4217 currency code; defaults to `BRL` |
| `time_zone` | `text` | No | IANA time-zone identifier reported by the browser during registration; defaults to `UTC` when unavailable or invalid |
| `created_at` | `timestamptz` | No | Creation time |
| `updated_at` | `timestamptz` | No | Last modification time |

Constraints and indexes:

- Primary key on `id`.
- Unique index on `lower(email)`.
- Currency code must contain three uppercase ASCII letters.

Email normalization and time-zone validation are application responsibilities before persistence.

The backend defines `BRL` as every new user's initial currency. The web client
sends the browser's IANA time zone as untrusted OAuth state; the backend validates
it before user creation and falls back to `UTC`. Users may change both preferences
after registration when profile settings are implemented.

### `auth_accounts`

Links a FinHand user to the stable identity assigned by Google. The `auth_`
prefix distinguishes identity-provider accounts from the financial `accounts`
table.

Important fields include the provider and provider account identifiers, the
owning `user_id`, Better Auth's optional OAuth token fields, granted scope, and
audit timestamps. `(provider_id, provider_account_id)` is unique, and `user_id`
references `users.id`. The TypeScript property remains `accountId` because that
is Better Auth's canonical field name, but it maps to the clearer PostgreSQL
column `provider_account_id`. FinHand currently uses Google only for identity,
so provider tokens are discarded before persistence. Email-and-password
authentication is disabled, so no credential account is created by the
application.

### `auth_sessions`

Stores Better Auth's server-side sessions. Each session has a unique opaque
token, expiration time, owning user, optional IP address and user-agent metadata,
and audit timestamps. The browser receives only the session cookie; protected
API routes resolve that cookie to a session and derive the authorized user ID.

### `auth_verifications`

Stores short-lived verification state required by Better Auth. Records contain
an identifier, value, expiration time, and audit timestamps. This table remains
part of the core authentication schema even though email/password and email
verification flows are not enabled.

### `accounts`

Represents where a user holds money or owes money, such as a checking account, savings account, cash wallet, or credit card.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `uuid` | No | Primary key |
| `user_id` | `uuid` | No | Owning user |
| `name` | `text` | No | User-defined account name |
| `type` | `text` | No | `cash`, `checking`, `savings`, `credit`, `investment`, or `other` |
| `currency_code` | `varchar(3)` | No | Account currency |
| `opening_balance_minor` | `bigint` | No | Signed opening balance in the currency's minor unit; defaults to `0` |
| `archived_at` | `timestamptz` | Yes | When the account was archived |
| `created_at` | `timestamptz` | No | Creation time |
| `updated_at` | `timestamptz` | No | Last modification time |

Constraints and indexes:

- Foreign key `user_id → users.id`.
- Check constraint for supported account types.
- Currency code must contain three uppercase ASCII letters.
- Index on `user_id`.
- Unique constraint on `(user_id, id, currency_code)` to support tenant- and currency-safe transaction references.

There is no stored `current_balance`. The balance is calculated from `opening_balance_minor` plus income minus expenses. A credit account can therefore have a negative net balance when money is owed.

An account referenced by transactions cannot be deleted; it must be archived.

### `categories`

Classifies income and expense transactions. Categories belong to one user and are never visible to or shared with other users.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `uuid` | No | Primary key |
| `user_id` | `uuid` | No | Owning user |
| `name` | `text` | No | User-defined category name |
| `type` | `text` | No | `income` or `expense` |
| `archived_at` | `timestamptz` | Yes | When the category was archived |
| `created_at` | `timestamptz` | No | Creation time |
| `updated_at` | `timestamptz` | No | Last modification time |

Constraints and indexes:

- Foreign key `user_id → users.id`.
- Check constraint for `income` or `expense`.
- Unique active category index on `(user_id, type, lower(name))` where `archived_at IS NULL`.
- Unique constraint on `(user_id, id, type)` to support tenant- and type-safe transaction references.
- Index on `user_id`.

FinHand seeds `Salary` as an income category and `Grocery` as an expense
category in each new user's private collection. Users can then rename, archive,
or extend those categories without affecting anyone else.

A category referenced by transactions cannot be deleted; it must be archived. Category hierarchy is deferred until there is a product requirement for it.

### `transactions`

Represents an authoritative financial event. AI output does not become a transaction until the user confirms it.

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `uuid` | No | Primary key |
| `user_id` | `uuid` | No | Owning user |
| `account_id` | `uuid` | No | Account affected by the transaction |
| `category_id` | `uuid` | Yes | Optional classification |
| `type` | `text` | No | `income` or `expense` |
| `amount_minor` | `bigint` | No | Positive amount in the currency's minor unit |
| `currency_code` | `varchar(3)` | No | Transaction currency; must match the account |
| `occurred_on` | `date` | No | Financial event's calendar date |
| `description` | `text` | No | Short user-facing description |
| `counterparty` | `text` | Yes | Merchant, payer, or payee |
| `notes` | `text` | Yes | Optional user notes |
| `origin` | `text` | No | `manual`, `document`, or `voice` |
| `created_at` | `timestamptz` | No | Creation time |
| `updated_at` | `timestamptz` | No | Last modification time |

Constraints and indexes:

- `amount_minor > 0`.
- Check constraints for transaction type and origin.
- Composite foreign key `(user_id, account_id, currency_code) → accounts(user_id, id, currency_code)`. This prevents cross-user account references and currency mismatches.
- Composite foreign key `(user_id, category_id, type) → categories(user_id, id, type)`. This prevents cross-user category references and ensures that an expense cannot use an income category. The relationship remains optional when `category_id` is null.
- Index on `(user_id, occurred_on DESC)` for timelines and summaries.
- Index on `(user_id, account_id, occurred_on DESC)` for account history.
- Index on `(user_id, category_id, occurred_on DESC)` for category summaries.

Amounts are always positive. `type` determines whether an amount adds to or subtracts from the user's net position. In TypeScript, `BIGINT` values must remain `bigint` or validated decimal strings and must not be converted to JavaScript `number` values.

`occurred_on` is a `DATE` because invoices and voice descriptions often provide a date without a precise time. Creation and update times remain time-zone-aware audit timestamps.

Transactions initially use the account's currency. Foreign exchange, exchange rates, and cross-currency transfers are outside the current requirements.

## Deletion and ownership rules

- User-scoped queries must always include the authenticated `user_id`.
- Composite foreign keys provide database-level protection against cross-user relationships.
- Row-level security should be evaluated in Milestone 2 after request authentication and database connection context are defined.
- Accounts and categories with transaction history are archived, not deleted.
- Deleting a user and all related financial data must be an explicit account-deletion workflow, not an incidental cascade from normal application operations.
- `updated_at` is maintained by application persistence logic unless a database trigger is intentionally introduced later.

## Planned extensions

The following entities are part of the planned architecture but not the first migration.

### Milestones 3 and 4 — uploads and AI extraction

#### `uploads`

Stores metadata for a user-owned object in Amazon S3:

- Owner and upload kind (`document` or `audio`)
- Private S3 object key, never a public URL
- Original filename, MIME type, byte size, and checksum
- Processing status and sanitized failure metadata
- Creation and update timestamps

#### `transaction_candidates`

Stores one structured transaction proposal extracted from a document or voice recording:

- Source upload and owning user
- Proposed account, category, type, amount, currency, date, description, and counterparty
- Field-level confidence or extraction metadata
- Status: `pending`, `confirmed`, or `rejected`
- Review timestamp
- Optional unique reference to the resulting transaction

One upload may produce multiple candidates. Confirmation must run in one database transaction: create the authoritative transaction, mark the candidate confirmed, and link the candidate to that transaction. Rejected or unreviewed candidates never appear in financial calculations.

#### `documents`

Stores document-specific processing state and extracted text for an eligible upload. Document content is sensitive financial data and must use the same ownership checks as transactions.

#### `audio_transcripts`

If transcript retention is approved, stores the transcription and processing metadata for an audio upload. Retention requirements should be decided before implementation to avoid storing sensitive speech unnecessarily.

### Milestone 5 — RAG

#### `document_chunks`

Stores ordered chunks of a document with page/source metadata, chunk text, and a pgvector embedding. The vector dimension and index type will be selected with the embedding model in Milestone 5 rather than fixed prematurely.

Retrieved chunks must be restricted to documents owned by the requesting user. Assistant answers should retain source references sufficient to show which document chunks grounded the response.

### Milestone 6 — AI usage metadata

An `ai_operations` table may store minimal operational metadata such as operation type, model, token counts, duration, status, and a Langfuse trace identifier. Prompts, document contents, transcripts, and credentials must not be copied into application logs.

## Deferred concepts

The initial model intentionally excludes concepts not present in the current product requirements:

- Budgets and savings goals
- Recurring transactions
- Split transactions
- Category hierarchies
- Transfers between accounts
- Exchange rates and multi-currency conversion
- Investment positions and tax lots
- Double-entry bookkeeping
- Mutable cached account balances

These can be added through focused migrations after their behavior and user experience are defined.
